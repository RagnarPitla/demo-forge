01Orientation

What Demo Forge is, and what it refuses to do

Capture measures. Design decides provenance. Scaffold generates. The gate proves. Every stage writes a file the next stage reads, so any stage can be re-run alone, and every claim the demo makes about the source app traces back to something a browser actually observed.

Project Mia was rebuilt by hand: a Power App at apps.powerapps.com became a static React click-through at mango-desert-0f88f590f.7.azurestaticapps.net. That took weeks of reading the app, copying its colours, rebuilding its screens and wiring a narration. Demo Forge is that process turned into tooling, so the second application costs hours instead of weeks.

You give it a URL and answer five questions. It gives you back a Vite + React application that looks like the source app, runs with no backend, carries a guided storyline, passes a headless render gate, and deploys to its own Azure Static Web App.

What it deliberately will not do

No backend

Seeded data only

Every value on screen comes from src/data/seed.js. There is no API, no database and no network call at runtime. The demo works on a plane.

No auth

Nobody signs in

The output has no login screen and no token handling. If the source app needs a session to capture, that session is used once, at capture time, and never ships.

No integrations

Nothing is live

Connectors, Dataverse, Graph and third-party services are represented visually and do nothing. A click that would write data in the real app shows the result instead.

No authorship

It will not decide what to say

Demo Forge reconstructs what the app looks like and how it moves. The argument the demo is making is yours. It asks for the storyline; it does not invent one.

The boundary that mattersDemo Forge is a faithfulness tool, not a cloning tool. It reproduces layout, design language, navigation and flow. It does not reproduce business logic, and it never claims to. A demo that quietly pretends to compute something is worse than one that visibly cannot.

04Stage 1

Intake: five questions before anything runs

No tool runs until these are answered. A capture aimed at the wrong audience produces a technically correct demo that nobody wants to show.

QuestionWhy it changes the output
1. What is the URL?Decides whether capture needs a session. A public marketing site captures cold; a Power App, a Dynamics form or an internal portal needs --login or a saved --profile.
2. Who is watching?An executive audience gets fewer screens and bigger claims. A practitioner audience gets the field-level detail. This sets how many routes are worth rebuilding at all.
3. What kind of demo?Four kinds, below. This is the single biggest branch in the whole pipeline.
4. What is the one thing they must remember?Becomes the spine of the storyline. If you cannot answer this, the demo has no argument and should not be built yet.
5. Where does it get shared?A link sent to a customer needs its own sub-site and containment. A link for an internal review can live on the front door.

The four demo kinds

Kind 1

Faithful replica

Rebuild the app as it is. Used to show a system to people who cannot be given access to it. Highest route count, no invented screens.

Kind 2

Guided walkthrough

The replica plus a narration that drives the viewer through one path. Steps advance on the viewer's own click. This is what Project Mia is.

Kind 3

Before and after

Two routes of the same screen: the system as it is, and the system as proposed. The argument lives in the difference, so both must be visually credible.

Kind 4

Vision cut

The captured design language applied to screens that do not exist yet. Honest only when it is labelled as such - the shell is real, the content is a proposal.

Say which kind it is, on the screenKinds 3 and 4 show things the source system does not do. The generated shell carries a banner slot for exactly this reason. A vision cut that is not labelled a vision cut is a credibility problem waiting for a follow-up meeting.

05Stage 2

Capture: finding the app inside the page

capture.mjs is 679 lines and the hardest part of the system. Loading a URL in Playwright is easy. Working out which part of what loaded is the application is not.

The iframe trap

A Power App URL does not serve the app. It serves a player - a thin host page whose job is to load the real application into a nested, sometimes cross-origin iframe. Screenshot the top frame and you get a loading chrome. Read the top frame's CSS and you get the player's tokens, not the app's.

So capture scores every frame in the page and picks the winner:

score = elements * 1
      + interactive * 40
      + customProps * 25
      + (themed     ? 3000 : 0)
      + (reactRoot  ? 1500 : 0)
      + min(text, 5000)

The two large constants do the real work. A player chrome has neither a theme block of CSS custom properties nor a React root; an application almost always has at least one. They are close to decisive on purpose - a frame that is themed beats a frame that merely has more DOM in it. Cross-origin frames throw on evaluate and are skipped rather than crashing the run.

Observed on the Mia source appweight=10011 els=183 props=163 themed=true - the app frame won by a margin no amount of player chrome could close.

Telling a route from a control

The crawler clicks things and watches what happens. The naive version treats every click that changes the view as a new route, which is how a sidebar collapse button became a page called /collapse-navigation-menu. Two defences now sit either side of the click.

A click that produces an already-seen signature is recorded under manifest.controls and its route slot is handed back to the crawler. On the Mia app that freed two slots, which then found two genuine routes - Configuration and WatchDog - that the earlier run had never reached.

The outline is node-budgeted, not depth-capped

Capture serialises the DOM into an outline the scaffold can read. The first version capped recursion at depth 7, which seemed generous. It was not: the navigation rail is deep, it comes first in document order, and it consumed the entire allowance before the traversal reached <main>. Every page came back with a nav and no content.

It now runs to depth 16 with a 1,200-node budget, and marks nav-like nodes with a chrome flag so the scaffold can skip them without losing them. On Mia the outline went from 39 nodes to 103.

What the PROBE measures on every page
MeasurementUsed for
customPropsEvery CSS custom property resolved on :root. The primary token source.
backgroundAreaPainted area per background colour, not element count. Decides canvas vs surface.
interactiveColorsColours used on buttons, links and inputs, weighted 2x foreground / 3x background. Decides the accent.
renderScaleDevice pixel ratio and zoom, so font sizes normalise back to CSS pixels.
outlineStructural tree with role, tag, text, box and the chrome flag.

06Stage 3

Design extraction: measured, not guessed

A named custom property beats an inferred role. Always. Inference is the fallback for apps that do not name their tokens, not the primary path.

This rule exists because the first version got it wrong four times out of four on a single app, and every one of those failures was confidently plausible.

RoleThe app's own :root saidInference saidWhy inference was wrong
canvas#f9fafb#ffffff wrongRanked backgrounds by element count. There are many cards and one canvas, so the cards won.
surface#ffffff#f9fafb wrongThe same error, inverted. Canvas and surface swapped places.
accent#4f46e5#22c55e wrongRanked by saturation. A success green is more saturated than an indigo, so a status colour became the brand.
text base13px10px wrong10px mono section labels out-counted 13px body copy. The most common size is not the base size.

All four fixes are in section 12 as before/after code. The shape of the fix in each case was the same: stop counting things, start measuring the thing that actually matters. Area instead of count. Where a colour is painted instead of how saturated it is.

Alias matching

ROLE_ALIASES maps 12 semantic roles to roughly six name patterns each, so --color-bg, --background, --surface-canvas and --app-bg all resolve to canvas. adoptSourceTokens() runs first and claims everything it can match; inferRoles() only fills what is left.

Provenance, in the file

:root {
  --canvas:  #f9fafb;  /* source --color-bg */
  --surface: #ffffff;  /* source --color-surface */
  --accent:  #4f46e5;  /* source --color-primary */
  --hairline:#e5e7eb;  /* 40 elements */
}

Anything with an /* N elements */ comment is inference and is the first place to look when a demo feels subtly off. Anything with /* source ... */ is a fact the app stated about itself.

Contrast is checked, not assumed

The design report includes a contrast table for every text-on-background pair the tokens imply. Adopting a source token verbatim can still produce an unreadable pair if the source app relied on a nuance the reconstruction drops, so the check runs regardless of provenance.

07Stage 4

Reconstruction: outline to React

scaffold.mjs reads the outline and classifies each region into one of three block kinds, then renders each kind with a primitive from the template.

BlockDetected whenRendered as
statsShort numeric-leading siblings in a row - a KPI strip.<Grid> of <StatTile>, values into seed.js
cardsSiblings that resemble each other: max/min width AND height ratio both ≤ 1.6.<Grid> of <Card>
panelEverything else with content - the fallback that stops siblings from vanishing.<Card> with a <SectionLabel>, tables become <DataTable>
The similarity test is the whole trickCards look like each other. A stack of sections does not - a header, a chart and a footnote have wildly different heights. Before the ratio test existed, that heterogeneous stack was classified as a card grid and the KPI strip came out mangled. Ratio ≤ 1.6 on both axes separates them cleanly.

The nine primitives

Everything the scaffold emits is built from src/shell/primitives.jsx: PageHeader, SectionLabel, Card, Grid, StatTile, DataTable, Button, Pill, Empty. Every one reads from tokens.css and hard-codes no colour. Re-running design against a different app restyles the entire demo without touching a component.

Depth has to match

A coupling worth knowing aboutcollectBlocks() in scaffold.mjs must traverse to the same depth as the capture outline. The stat strip on the Mia home page sits at depth 9. A cap of 6 rendered that page as visibly "not reconstructed" while every gate still passed, because the gate checks that a page has content, not that it has the right content.

08Stage 5

Storyline: the guided-step contract

src/demo/guide.js is 357 lines and implements one idea: a guided demo advances when the viewer does something, never when a clock says so.

{
  target:     () => document.querySelector('[data-testid="kpi-waves"]'),
  event:      'click',
  placement:  'bottom',
  gap:        12,
  isComplete: () => location.hash.endsWith('/waves'),
  kicker:     'Where the work lives',
  script:     'Eight tasks across three waves. Nothing is assigned yet.',
  onEnter:    () => highlightWave(2)
}
FieldBehaviour
targetA function, not an element. Resolved at step time, so it works on content that has not rendered yet.
eventWhat the viewer must do. The step will not advance on anything else.
isCompleteThe truth test. The step is done when the app is actually in the expected state, not when the click fired.
script / kickerWhat the presenter says. This is the part you write; Demo Forge generates a placeholder and nothing more.
onEnterOptional side effect - open a panel, seed a filter, scroll something into view.

Advance on action, never on a timer

There is no setTimeout in the advance path at all.

Why: a timed tour races the person watching it. They ask a question, the tour moves on without them, and the presenter spends the rest of the demo apologising to the UI.

A missing target parks. It does not skip.

If target() returns nothing, the tour holds position and keeps re-resolving.

Why: silently skipping means the demo quietly drops the step that carried the argument, and nobody notices until the meeting. Parking is visible, and visible is fixable.

Audiences and containment

demo-forge audience /Exec-brief --guided adds a registry entry and a script file. Every audience gets its own route prefix, and scope.js mirrors the whole route table beneath that prefix.

09Stage 6

Verify: three gates that must go green

A generated demo is not finished when it builds. It is finished when a headless browser has opened every screen and found real content on each one.

GateLinesWhat it proves
verify-render.mjs158Every route renders content, throws no console error, and every audience stays inside itself.
verify-routes.mjs48No duplicate route paths, and every nav item resolves to a route that exists.
verify-audiences.mjs51Every registry entry has a script, and every script is reachable from a registry entry.

The render gate's assertion

elements >= 12
  && text > 0
  && errors.length === 0
  && (!expectContained || containment.stayed)

The floor of 12 elements is low on purpose. Its job is to catch a screen that rendered a shell and nothing else - the single most common way a generated demo fails, and the one that is hardest to spot by eye because the page still looks like an application.

A gate that counted wrong is worse than no gateThe first version reported routes: 14 for an app with 7, because its regex matched both the routes array and the navItems array. Every route was tested twice and the pass looked twice as thorough as it was. The same bug in verify-routes.mjs made its duplicate check useless: every path legitimately appeared twice, so the check could never fire. Both are fixed in section 12.

10Stage 7

Deploy: Azure Static Web Apps

deploy.mjs is a thin wrapper over the az CLI - preflight, createSwa, deployStatus, envName. It is thin because the value is in the constraints it enforces, not the commands it runs.

ConstraintWhat it means in practice
Environment name is a suffixAzure owns the hostname and only appends: <app>-<env>.azurestaticapps.net. A prefix host cannot be created. Asking for one wastes an afternoon.
Alphanumeric, 16 characters maxNo hyphens inside the environment name. sapsfdc, never sap-sfdc. envName() normalises and truncates so this fails at intake rather than at deploy.
Custom domains are production-onlyA named environment cannot have one. If the demo needs a branded URL it has to be the production slot.
Quota: 3 on Free, 10 on StandardNamed environments are capped. On Free this binds fast - the fourth branch fails at the deploy step with maximum number of staging environments while everything else still passes.
Deploys run on push, not on PRA pull request does not create a preview URL. Work in progress is reviewed on its own branch subdomain.
The one that will bite youAn empty deployment_environment in the workflow means production. It does not mean "no environment" and it does not mean "skip". A branch with a blank value overwrites the live site. preflight refuses to proceed when it finds one.

demo-forge deploy --dry-run prints the exact resource group, app name, environment name and hostname it would create, and touches nothing. Run it first, every time.

11Rationale

Design decisions and the reasoning behind them

A named source token beats an inferred role

Inference runs only on roles the source app did not name.

Why: inference got all four primary roles wrong on the first app it met, and every wrong answer was plausible enough to ship. An app that names its tokens is telling you the answer; guessing over the top of it is not cleverness.

Measure area and position, not frequency

Canvas is decided by painted area. Accent is decided by where a colour appears, not how saturated it is.

Why: counting elements answers "what is most repeated", which is almost never the same question as "what is most important". One canvas outweighs forty cards.

Budget nodes, do not cap depth

Depth 16 with a 1,200-node ceiling, instead of a hard depth limit.

Why: a depth cap spends the whole allowance on whatever comes first in document order, which is the navigation rail. The budget lets a deep-but-narrow content tree through while still bounding the total.

Every generated token carries provenance

/* source --color-bg */ versus /* 40 elements */, inline in the CSS.

Why: when a stakeholder challenges a colour, the answer should be a grep rather than a recollection. It also makes the inference surface obvious - those are the tokens to check first when a demo feels subtly wrong.

Each sub-site stays inside itself

Navigation inside an audience prefix can never resolve to the shared front door.

Why: these links get sent to different customers. Someone in the SAP walkthrough pressing Home must not land on another customer's story. This is a containment guarantee, enforced by a test, not a convention.

A merge adds a URL; it never replaces the front door

Adding an audience adds a route. It does not change what a visitor sees at the root.

Why: the front door is a deliberate decision, not a side effect of whoever shipped last. Changing it should require someone to choose to change it.

Reject unknown flags instead of defaulting

Every command declares a FLAGS allowlist; anything outside it is an error.

Why: --app was not recognised, so it fell through to a default directory and the whole build landed somewhere else entirely, silently, with a success message. A typo must fail loudly or it will cost an hour.

Keep the capture manifest

capture/manifest.json ships with the demo rather than being cleaned up.

Why: it is the only evidence that the reconstruction matches the source. Without it, "does their app really look like this" is unanswerable six weeks later.

Fix 1 - canvas by painted area, not element count

lib/design.mjs · the canvas came back #ffffff when the app's own value was #f9fafb

Before - counts elements
const bg = probe.backgrounds;// most common background winsconst ranked = Object.entries(bg) .sort((a, b) => b[1].count - a[1].count);roles.canvas = ranked[0][0];roles.surface = ranked[1][0];
After - measures painted area
const bg = probe.backgroundArea;// the colour covering the most pixels is the canvas,// however few elements paint itconst ranked = Object.entries(bg) .sort((a, b) => b[1].area - a[1].area);roles.canvas = ranked[0][0];roles.surface = ranked[1][0];
The general lessonForty cards outnumber one canvas, so counting picks the cards. One canvas covers more of the screen than forty cards, so area picks the canvas. The question was never "what repeats most".

Fix 2 - accent by where it is painted, not how saturated it is

lib/design.mjs · the accent came back #22c55e (a success green) when the brand was #4f46e5

Before - saturation contest
const candidates = allColors .map(c => ({ c, s: saturation(c) })) .sort((a, b) => b.s - a.s);roles.accent = candidates[0].c;
After - weighted by interactive surface
// only colours used on buttons, links and inputsconst scored = probe.interactiveColors.map(e => ({ c: e.color, w: e.asForeground * 2 + e.asBackground * 3})).sort((a, b) => b.w - a.w);roles.accent = scored[0].c;

Background weight is 3 and foreground 2 because a filled primary button is a stronger brand signal than a coloured link.

Fix 3 - base text size normalised for render scale

lib/design.mjs · base came back 10px when the app's own value was 13px

Before - raw, most frequent
const sizes = probe.fontSizes;const base = mostFrequent(sizes);scales.text = { base };
After - normalised, body-copy weighted
const k = probe.renderScale || 1;const sizes = probe.fontSizes.map(f => ({ px: Math.round(f.px / k), chars: f.textLength // weight by text, not tags}));const base = weightedMode(sizes, 'chars');scales.text = { base };

Section labels are numerous but carry three words each. Body copy is rarer per element and carries paragraphs. Weighting by characters asks the right question.

Fix 4 - adopt the source tokens before inferring anything

lib/design.mjs · the root cause under fixes 1 to 3 - the app named 163 properties and none were read

Before - inference only
export function buildTokens(probe) { const roles = inferRoles(probe); const scales = inferScales(probe); return emit(roles, scales);}
After - source first, inference fills gaps
export function buildTokens(probe) { const roles = adoptSourceTokens(probe.customProps); inferRoles(probe, roles); // only unfilled roles const scales = adoptSourceScales(probe.customProps); inferScales(probe, scales); return emit(roles, scales); // each carries provenance}

ROLE_ALIASES maps 12 roles to about 6 name patterns each, so --color-bg, --background, --surface-canvas and --app-bg all land on canvas.

Fix 5 - a nav toggle is not a route

lib/capture.mjs · produced a phantom page called /collapse-navigation-menu

Before - any view change is a route
for (const el of clickables) { await el.click(); await settle(page); if (viewChanged()) { routes.push(routeFrom(el)); }}
After - filtered, then signature-tested
for (const el of clickables) { if (isDisclosure(el)) { controls.push(el); continue; } await el.click(); await settle(page); const sig = await contentSignature(page); if (seen.has(sig)) { controls.push(el); continue; } seen.add(sig); routes.push(routeFrom(el));}
Before - no pre-filter existed
// nothing
After - ARIA says what a control is
const isDisclosure = el => el.hasAttribute('aria-expanded') || el.hasAttribute('aria-controls') || el.hasAttribute('aria-haspopup');// signature ignores chrome, or a collapsing rail// would change the digest and look like a pageconst CHROME = 'nav,[role=navigation],[class*=sidebar],' + '[class*=rail],header,[class*=topbar]';

Fix 6 - the gate was counting every route twice

Fix 8 - budget the outline, do not cap its depth

lib/capture.mjs · every page came back with a navigation rail and no content

Before - hard depth cap
function walk(node, depth) { if (depth > 7) return null; return { tag: node.tagName, children: [...node.children] .map(c => walk(c, depth + 1)) };}
After - node budget and a chrome flag
let budget = 1200;function walk(node, depth) { if (depth > 16 || budget-- <= 0) return null; return { tag: node.tagName, chrome: node.closest(CHROME) !== null, children: [...node.children] .map(c => walk(c, depth + 1)) };}
The coupled changecollectBlocks() in scaffold.mjs had to move to depth 16 to match. The Mia stat strip sits at depth 9; with the scaffold still capped at 6, the outline was correct and the page still rendered as if nothing had been reconstructed. Outline depth is 39 nodes before, 103 after.

15Using it

Limits, gaps and known risks

Untested

Authenticated capture

The --login and --profile paths have never been run. Exercising them needs a real tenant session. Assume the first authenticated capture will need debugging, and budget for it.

Unproven

Non-SPA route discovery

The crawler was built and tested against a single-page application. A server-rendered site with real page loads is a different traversal problem and has not been validated.

Structural

Unnamed design systems

An app with no CSS custom properties falls back entirely to inference - the path that got all four roles wrong before it was fixed. The fixes make it better, not correct. Check the provenance comments.

Structural

Canvas and WebGL

Anything drawn rather than laid out is invisible to the DOM probe. Charts rendered to canvas come back as an empty box and need a hand-built placeholder.

Quota

Three Free environments

On the Free SKU only three named environments exist at once. The fourth demo fails at deploy while every gate still passes, which reads as a tooling bug and is not one.

Judgement

The gate cannot check meaning

It proves a page has content. It cannot prove the content is the right content. Bug 8 passed every gate while rendering a visibly broken page. Look at the screens.

The failure mode to watch forEvery one of the eight bugs produced output that looked correct. Wrong colours look like a design choice. A phantom route looks like a page you forgot about. A double-counted gate looks like extra thoroughness. The only defence that worked was diffing the tool's output against the source app's own values - so do that on the first run against any new application, before writing a line of storyline.

16Using it

Runbook: your next demo, start to finish

  1. Answer the five intake questions out loud. If you cannot state the one thing the audience must remember, stop - the demo has no argument yet and rebuilding screens will not give it one.
  2. Run doctor. Thirty seconds, and it fails on the missing dependency rather than halfway through a capture.
  3. Capture with --routes set slightly high. Discovering twelve screens and using six is cheap. Re-crawling because you capped at five is not.
  4. Open src/theme/tokens.css and read the provenance comments. Anything marked /* N elements */ is a guess. Compare those against the source app's :root in devtools before going further.
  5. Open the generated app and look at every screen. The gate proves content exists; your eyes prove it is the right content. This is the step that catches a depth-cap class of bug.
  6. Register the audience before writing the storyline. audience /Name --guided creates the script file the steps go into, and the route prefix the link will use.
  7. Write the steps. One per thing the viewer must do. Set isComplete honestly - it is the difference between a tour that waits for the room and one that races it.
  8. Run verify --render. Green on every screen, including containment.
  9. Run deploy --dry-run, read the plan, then deploy. Confirm the environment name is a suffix, alphanumeric and at most 16 characters, and that you have a free slot in the quota.
  10. Send the audience URL, not the root. Containment only protects the person who arrives inside the sub-site.
The honest time estimateA cold build against a public SPA is minutes. Reviewing the tokens and the screens is the better part of an hour. The storyline is as long as the argument takes to write, and is the only part no tool can shorten. Project Mia took weeks by hand; the second application is a day, and most of that day is judgement rather than reconstruction.

17Latest change

Directed capture: you give the clicks, it follows them

The original capture stage had one mode. It crawled: seeded a queue from the entry route's navigation, ranked the candidates, and visited whatever it decided looked like a route. That answers what is in this app. It does not answer show me the approval path and not the settings page, which is the question you actually have in front of a customer.

Directed capture is the other half. You supply an ordered instruction list, it performs each one against the live app and records a screen after each. The instruction list doubles as the outline of the storyline the demo will narrate, so the beats you type become the beats you speak.

The crawler optimises for coverage. A demo needs a path. Those are different objectives and they need opposite behaviour at the one point that matters, which is why they are separate loops rather than one loop with a flag.

Change 1 - the reset, which is the whole architectural point

The crawler returns to the entry URL before every hop. That is correct for a crawler and wrong for a sequence.

lib/capture.mjs · the crawler replays from the entry URL; directed capture must not

Before - one loop, and it resets
while (queue.length && routes.length < maxRoutes) { const job = queue.shift(); if (job.via !== 'entry') { // an SPA's state machine is not guaranteed reversible await page.goto(url, { waitUntil: 'domcontentloaded' }); await settle(page, waitMs); // ...then replay the single click for this job }
After - directed mode never resets
await record('Home', 'entry');for (const step of steps) { // your steps are a sequence; a sequence accumulates state const frame = await findAppFrame(page); const res = await runStep(page, frame, step, { waitMs, settle }); if (res.recorded) await record(res.label, `step:${step.verb}`);}

Open a project, then open its documents. Reset between those two clicks and the second one lands on an empty documents list, records the wrong screen, and reports success. The cost of not resetting is that a failed step invalidates everything after it, which is precisely why a step that cannot be performed throws instead of continuing.

Change 2 - one recorder, two callers

The screenshot, DOM dump, outline write and routes.push() were inline in the crawl loop. Two modes writing two versions of that block would eventually produce two manifest shapes, and the scaffold reads exactly one.

Change 3 - the resolver must survive a Content-Security-Policy

The first draft passed the resolver into the page as a source string and called eval() on it. A page with a strict CSP blocks eval, and that is exactly the kind of well-built application this tool is most likely to be pointed at. Playwright serialises a real function over CDP instead, which CSP does not touch.

lib/steps.mjs · eval() in page context replaced by a serialised function

Before - eval in page context
export const RESOLVE = `(() => { /* ...resolver source... */ })()`;await frame.evaluate(([resolveSrc, target, k, value]) => { const resolve = eval(resolveSrc); const r = resolve(target, k);}, [RESOLVE, step.target, kind, step.value]);
After - a function, serialised by Playwright
function actInPage([target, kind, value]) { // resolution and the action, inlined - nothing is stringified /* data-testid -> label[for] -> exact name -> unique substring */}await frame.evaluate(actInPage, [step.target, kind, step.value ?? '']);

The storyline scaffold generated one beat per route, in route order. A crawl has no intended order so that was the best available. A directed capture has one, written to the manifest as a timeline.

Change 5 - the ninth bug, found by using the feature

The first end-to-end directed run died with No capture.json in /private/tmp/forge-proof/demo-build/capture. In capture, --out means the capture directory; in scaffold, it means the app directory. One flag, two meanings, silently pointing the two stages at the same path.

The instruction language

InstructionDoesRecords a screen
click <target>Clicks the matching elementYes
type <text> into <target>Fills an input through the native setterYes
fill <target> with <text>The same, said the other way roundYes
wait <ms> / wait <n> sPausesNo
capture [as <name>]Forces a named screen even if content repeatsYes
goto <url> [as <name>]NavigatesYes
backBrowser backYes

Target resolution runs widest-first on visible elements inside the app frame: exact data-testid, then a <label for> for typing targets, then an exact accessible name, then a unique substring. Exact beats substring so click Home cannot select "Home office spend". A substring matching more than one element is rejected, not resolved to the first hit - picking one of three is how a directed capture silently records the wrong screen.

A failed step stops the run, and tells you why

This is not an error path bolted on afterwards. It is the discovery mechanism: guess a label, read the refusal, write the real steps. Faster than reading the app's source, and it cannot go stale.

Revisits are not duplicate routes

Clicking the nav item for the screen you are already on is a real thing a person does, and it is not a second page. The first directed run emitted home and Overview as two byte-identical routes. Directed mode now reuses the crawler's content-signature test: a repeat points the timeline at the screen that already exists and says so out loud.

> click Overview
   "Overview" is the screen already captured as "home" - revisit, not a new route

capture as <name> is exempt, because that is an explicit request for a named screen.
